# Лінійний пошук (Linear Search): покроковий розбір

**Лінійний пошук** — найпростіший алгоритм пошуку: щоб знайти значення `x` у масиві, ми **послідовно перевіряємо кожен елемент зліва направо** й порівнюємо його з `x`. На першому збігу повертаємо **індекс** цього елемента; якщо дійшли до кінця без збігу — повертаємо `-1`. Масив при цьому **не змінюється** і не потребує жодної передумови — пошук однаково працює на **невпорядкованих** даних.

На відміну від сортувань, тут немає ані обмінів, ані зсувів: єдина «ціна» алгоритму — **кількість перевірок** (порівнянь `arr[i] == x`). Зате надзвичайно наочно різняться випадки: найкращий — коли елемент спереду (одна перевірка, $O(1)$), гірший — коли він у кінці або відсутній (повний скан, $O(n)$).

## 1. Інтуїція: полиця книжок

Уявіть, що шукаєте потрібну книжку на полиці, **проглядаючи її зліва направо** — одну за одною, доки не натрапите на потрібну (або не дійдете до кінця полиці). Саме так працює лінійний пошук: курсор-«бігунець» іде нерухомим масивом і перевіряє кожну комірку по черзі.

![Скан зліва направо в пошуку 8](docs/images/scan_intuition.png)

Поточну комірку (яку перевіряємо *зараз*) позначаємо **рожевим**. Щойно знайшли збіг — комірка стає **зеленою**, і пошук спиняється: решту масиву далі переглядати не треба.

## 2. Ідея методу: перевіряй по черзі

Працюємо з масивом із 5 елементів. Він **нерухомий** — пошук його не переставляє:

| індекс | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| **значення** | 5 | 3 | 8 | 1 | 4 |

![Масив [5, 3, 8, 1, 4] як ряд комірок](docs/images/array_main.png)

Алгоритм складається з одного циклу: для кожного індексу `i` від `0` до `len(arr)-1` перевіряємо, чи `arr[i] == x`. Якщо так — одразу повертаємо `i` (далі шукати немає сенсу). Якщо цикл дійшов до кінця й жодна перевірка не дала збігу — елемента в масиві немає, повертаємо `-1`.

## 3. Два виходи: індекс або існування

З лінійного пошуку природно виходять **два режими**:

- `linear_search(arr, x)` — повертає **індекс** першого збігу (або `-1`);
- `exists_in_list(arr, x)` — повертає **булеве** значення: чи є `x` у масиві взагалі (просто перевіряє, що індекс не `-1`).

Перший потрібен, коли важливо *де саме* лежить елемент; другий — коли цікавить лише *факт наявності*.

## 4. Приклад — масив `[5, 3, 8, 1, 4]`, шукаємо `8`

### Базова реалізація

Ось базова реалізація — її ми й розбираємо рядок за рядком (повна версія з документацією — у [`linear_search/core.py`](linear_search/core.py)):

```python
def linear_search(arr, x):
    for i in range(len(arr)):
        if arr[i] == x:
            return i
    return -1

def exists_in_list(arr, x):
    return linear_search(arr, x) != -1

numbers = [1, 3, 5, 7, 9, 11]
print(linear_search(numbers, 7))      # 3
print(exists_in_list(numbers, 7))     # True
print(exists_in_list(numbers, 2))     # False
```

Що тут що:

- `for i in range(len(arr))` — **цикл**: перебираємо індекси `0, 1, …, len(arr)-1` зліва направо;
- `if arr[i] == x` — **перевірка** (порівняння): чи поточний елемент дорівнює шуканому;
- `return i` — якщо так, **збіг** — повертаємо індекс і одразу виходимо (перший збіг);
- `return -1` — якщо цикл завершився без збігу, елемента **немає** в масиві.

`exists_in_list` лише викликає `linear_search` і перетворює його результат на `True`/`False`.

Навчальна версія [`linear_search_steps`](linear_search/core.py) повторює цей код **дія в дію**, але після кожної перевірки записує знімок стану й лічильник перевірок — саме з цих знімків зібрані всі картинки нижче.

### Як читати кадри

- 🌸 **рожева комірка з курсором ▼** — елемент, який перевіряємо *зараз* (`arr[i] == x?`);
- ⬜ **нейтральні комірки** — ще не перевіряли;
- 🩶 **приглушені комірки з ✗** — уже перевірили й відкинули (не той);
- 🟢 **зелена комірка з ✓** — знайдений збіг (курсор спиняється тут);
- угорі — **бейдж «шукаємо: x»**, під кадром — **вердикт** перевірки та **лічильник** перевірок.

![Перевірка 2: 3 ≠ 8](docs/images/step_main_1.png)

**Перевірка 3** (`i = 2`): `arr[2] = 8`. Збіг! Повертаємо індекс `2` і спиняємо пошук:

## 5. Аналіз випадків — головний акцент

Скільки перевірок зробить лінійний пошук, залежить від того, **де** (і чи взагалі) лежить шуканий елемент. Для пошуку ця різниця набагато наочніша, ніж для сортувань:

![Порівняння випадків: найкращий, гірший, відсутній, середній](docs/images/cases.png)

```text
Аналіз випадків лінійного пошуку

Найкращий випадок — 5 спереду (індекс 0)
  → перевірок: 1, результат: 0
Гірший випадок (знайдено) — 4 у кінці
  → перевірок: 5, результат: 4
Відсутній елемент (гірший) — повний скан до -1
  → перевірок: 5, результат: -1
Середній випадок — 8 приблизно посередині
  → перевірок: 3, результат: 2
```

- **Найкращий випадок $O(1)$:** елемент спереду — одна перевірка, і ми вже знайшли.
- **Гірший випадок $O(n)$:** елемент у самому кінці — щоб до нього дійти, перевіряємо **весь** масив.
- **Відсутній елемент $O(n)$:** збігу немає взагалі — теж повний скан до `-1` (стільки ж перевірок, що й гірший-знайдено).
- **Середній випадок $\approx n/2$:** якщо елемент із рівною ймовірністю на будь-якій позиції, у середньому перевіряємо половину масиву.

### Складність і контраст із двійковим пошуком

Лінійний пошук — це $O(n)$: кількість перевірок росте **лінійно** з розміром масиву. Для **невпорядкованих** даних це неминуче — інакше елемент знайти не можна. Але якщо масив **відсортований**, двійковий пошук дає $O(\log n)$, щоразу відкидаючи половину:

![Графік: лінійний O(n) проти двійкового O(log n)](docs/images/growth.png)

На відсортованому масиві з мільйона елементів лінійний пошук у гіршому випадку зробив би до **мільйона** перевірок, а двійковий — близько **двадцяти**. Це і є місток до [наступного кроку](#series) — двійкового пошуку.


## 7. Вартовий (sentinel) як мікрооптимізація

У базовому циклі кожна ітерація робить насправді **дві** перевірки: чи не вийшли за межі масиву (службова, неявна в `for`) і чи це шуканий елемент (`arr[i] == x` — корисна). Класична мікрооптимізація — **вартовий** (sentinel): дописуємо `x` у кінець як «вартового», тож збіг **гарантований** щонайпізніше на ньому. Тепер перевірку меж можна прибрати — лишається тільки корисне порівняння:

```python
def linear_search_sentinel(arr, x):
    n = len(arr)
    a = list(arr)
    a.append(x)             # вартовий: збіг тепер гарантований
    i = 0
    while a[i] != x:        # без перевірки меж: вартовий зупинить цикл
        i += 1
    return i if i < n else -1
```

Результат — **той самий індекс**, що й у базовій версії (а працюємо з копією, тож вхідний масив не змінюється):

```text
Вартовий (sentinel) проти базового пошуку — однаковий індекс, менше службових перевірок
  базовий пошук: індекс 2, перевірок меж за ітерацію — 1
  вартовий: індекс 2, перевірок меж за ітерацію — 0
```

Асимптотику це не змінює (так само $O(n)$), але прибирає одне службове порівняння з кожної ітерації гарячого циклу.

## 11. Складність і властивості

Скільки роботи робить лінійний пошук, залежить від позиції шуканого елемента:

| Випадок | Перевірки | Коли трапляється |
|---|---|---|
| **Найкращий** | $O(1)$ | елемент спереду (індекс 0) |
| **Середній** | $O(n)$, $\approx n/2$ | елемент десь усередині |
| **Гірший** | $O(n)$ | елемент у кінці **або** відсутній (повний скан) |

Інші властивості:

- **Не змінює масив:** пошук лише *читає* елементи; додаткова пам'ять — $O(1)$ (вартовий потребує копії, тобто $O(n)$).
- **Без передумов:** працює на **невпорядкованих** даних — на відміну від двійкового пошуку, який вимагає відсортованого масиву.
- **Метрика — кількість перевірок** (порівнянь `arr[i] == x`); жодних обмінів чи зсувів, як у сортуваннях, немає.
- **Перший збіг при дублікатах:** `linear_search` повертає найлівіший збіг; усі входження дає `find_all`.

## 12. Обмеження: коли лінійний пошук програє

Лінійна складність означає, що для **великих** масивів пошук стає повільним: щоб знайти елемент серед мільйона, у гіршому разі доведеться зробити мільйон перевірок. Якщо дані **відсортовані**, двійковий пошук разюче швидший:

| `n` | Лінійний ($\approx n$) | Двійковий ($\approx \log_2 n$) | У скільки разів швидше |
|---|---|---|---|
| 10 | 10 | ≈ 4 | ~2× |
| 100 | 100 | ≈ 7 | ~14× |
| 1 000 | 1 000 | ≈ 10 | ~100× |
| 1 000 000 | 1 000 000 | ≈ 20 | ~50 000× |

Але цей виграш має **ціну-передумову**: масив треба тримати відсортованим. Якщо дані невпорядковані, є лише два шляхи — або шукати лінійно за $O(n)$, або спершу відсортувати за $O(n\log n)$ і потім шукати двійково. Заради **одного** пошуку сортувати невигідно; лінійний пошук тут — єдиний розумний варіант:

| Алгоритм | Час | Передумова | Особливість |
|---|---|---|---|
| **Лінійний пошук** | $O(n)$ | **немає** | працює всюди, зокрема на невпорядкованих даних |
| Двійковий пошук | $O(\log n)$ | відсортований масив | швидкий, але потребує попереднього сортування |
| Хеш-таблиця | $O(1)$ у середньому | побудована хеш-структура | найшвидший доступ ціною пам'яті й передобробки |

## 13. Де це доречно

Ніша лінійного пошуку — саме там, де передумови двійкового не виконуються або не окупаються:

- **Невпорядковані дані.** Немає сортування — немає двійкового пошуку; лінійний працює без жодних умов.
- **Малі набори.** На кількох елементах різниця $O(n)$ vs $O(\log n)$ непомітна, а код простіший.
- **Зв'язні списки.** Немає доступу за індексом — двійковий пошук неможливий, лишається послідовний прохід.
- **Потокові / разові пошуки.** Дані надходять по одному або шукаємо лише раз — сортувати заради одного запиту невигідно.
- **Пошук за складною умовою** (`find_all`, перший елемент, що задовольняє предикат) — там, де «впорядкованості за ключем» просто немає.

## 14. Місце в серії: перший крок до пошуку

Це **перший алгоритм пошуку** в серії — після кількох алгоритмів **сортування**. І зв'язок між ними прямий: лінійний пошук працює на будь-яких даних, але повільно ($O(n)$); двійковий — швидко ($O(\log n)$), але лише на **відсортованих**. Отже, попередні розбори сортувань саме й **уможливлюють** швидкий пошук:

| Тема | Репозиторій |
|---|---|
| Бульбашкове сортування | [algo-bubble-sort](https://github.com/MarynaShavlak/algo-bubble-sort) |
| Сортування вставками | [algo-insertion-sort](https://github.com/MarynaShavlak/algo-insertion-sort) |
| Сортування вибором | [algo-selection-sort](https://github.com/MarynaShavlak/algo-selection-sort) |
| Швидке сортування | [algo-quick-sort](https://github.com/MarynaShavlak/algo-quick-sort) |
| Сортування злиттям | [algo-merge-sort](https://github.com/MarynaShavlak/algo-merge-sort) |
| Сортування Шелла | [algo-shell-sort](https://github.com/MarynaShavlak/algo-shell-sort) |
| Порозрядне сортування | [algo-radix-sort](https://github.com/MarynaShavlak/algo-radix-sort) |

**Куди далі:** двійковий пошук ($O(\log n)$ на відсортованих даних) — природний наступний крок, що завершує зв'язку «спершу впорядкуй, потім швидко шукай».

## 15. Підсумок

- **Лінійний пошук** послідовно перевіряє кожен елемент зліва направо, доки не знайде `x` (повертає його індекс) або не дійде до кінця (повертає `-1`).
- Працює **на місці й тільки читає** масив ($O(1)$ пам'яті) і **не потребує впорядкованих даних** — головна перевага перед двійковим пошуком.
- **Складність:** $O(1)$ у найкращому випадку (елемент спереду), $O(n)$ у середньому ($\approx n/2$) та гіршому (елемент у кінці або відсутній).
- **Два режими:** `linear_search` дає індекс (або `-1`), `exists_in_list` — булеве існування; при дублікатах повертається **перший** збіг, а всі входження дає `find_all`.
- **Вартовий (sentinel)** — класична мікрооптимізація: прибирає перевірку меж із кожної ітерації, не змінюючи результату.
- На масиві `[5, 3, 8, 1, 4]` пошук `8` коштує **3 перевірки** (збіг на індексі 2); найкращий випадок — **1 перевірка**, гірший і відсутній — **5** (повний скан).
- Для **великих відсортованих** масивів лінійний пошук програє двійковому ($O(n)$ проти $O(\log n)$), але для **невпорядкованих** даних, малих наборів, зв'язних списків і разових пошуків він — єдиний розумний вибір.
