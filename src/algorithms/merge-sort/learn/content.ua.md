# Сортування злиттям (Merge Sort): покроковий розбір

**Сортування злиттям** — класичний ефективний метод, що працює за принципом **«розділяй і володарюй»** (його запропонував Джон фон Нейман ще 1945 року). Ідея проста: **поділи** масив навпіл, окремо відсортуй кожну половину (рекурсивно — тим самим методом), а тоді **злий** дві вже відсортовані половини в один відсортований масив. Поділ триває, доки не лишаться поодинокі елементи (вони вже відсортовані), після чого половинки зливаються знизу вгору.

На відміну від простих $O(n^2)$-сортувань і навіть від швидкого сортування, merge sort дає **гарантований** $O(n\log n)$ **у будь-якому випадку** — найкращому, середньому й гіршому: немає вхідних даних, що його «ламають». Він **стабільний** і чудово лягає на зовнішнє сортування, зв'язні списки та паралелізм. Ціна за ці гарантії — $O(n)$ додаткової пам'яті (метод **не on-place**). Саме merge sort разом із сортуванням вставками лежить в основі **TimSort** — стандартного `sorted()` / `list.sort()` у Python.

## 1. Інтуїція: розділяй і володарюй

Уявімо масив як рядок **комірок** зі значеннями. Сортування злиттям не порівнює всі пари підряд — воно **ділить задачу навпіл**: щоб відсортувати масив, досить відсортувати дві його половини, а потім **злити** їх. Злити два **вже відсортовані** списки легко й швидко — іти ними одночасно й щоразу брати менший із двох «передніх» елементів:

![Розділяй і володарюй: поділ навпіл, потім злиття відсортованих половин](docs/images/idea_intro.png)

Кожну половину сортуємо так само — ділимо ще навпіл, — аж поки не лишаться **поодинокі елементи**: список з одного елемента вже відсортований. Тоді починається зворотний хід: половинки **зливаються знизу вгору** в усе більші відсортовані відрізки, доки не утвориться весь відсортований масив. Саме одне таке злиття двох половин — крок за кроком — виглядає так:

![Розбір однієї операції злиття двома вказівниками](docs/images/idea_merge_steps.png)

## 2. Ідея методу: поділ навпіл і злиття

Алгоритм складається з двох функцій:

1. **`merge_sort`** ділить масив навпіл **за позицією** (`mid = len(arr) // 2`), рекурсивно сортує обидві половини й повертає результат їх злиття. Базовий випадок — список із ≤ 1 елемента: він уже відсортований.
2. **`merge`** зливає дві відсортовані половини двома вказівниками: порівнює їхні «голови», додає менший у результат і рухає відповідний вказівник; коли один список вичерпано — «доливає» решту іншого.

Ключова відмінність від швидкого сортування (теж «розділяй і володарюй»): quicksort робить роботу **до** рекурсії (розбиває за опорним елементом), а merge sort — **після** рекурсії (зливає дві відсортовані половини). Тому головна робота тут — у фазі **злиття**.

## 3. Чому дерево завжди збалансоване

Оскільки поділ **строго навпіл за позицією** (а не за значенням опорного, як у quicksort), ліва й права половини завжди відрізняються щонайбільше на один елемент. Тому **дерево рекурсії завжди збалансоване**, а його глибина — рівно $\lceil\log_2 n\rceil$ для **будь-якого** входу.

Звідси й головна перевага: на кожному з $\log n$ рівнів злиття опрацьовує загалом $n$ елементів, тож разом виходить $O(n\log n)$ — **гарантовано, незалежно від порядку вхідних даних**. У quicksort невдалий вибір опорного може зробити дерево виродженим (глибина $n$) і дати $O(n^2)$; у merge sort такого випадку **не існує** в принципі.

## 4. Приклад — масив `[8, 4, 6, 2, 7, 1, 5, 3]`

Працюємо з масивом із 8 елементів (степінь двійки — дерево поділу виходить ідеально збалансованим, глибина 3).

### Базова реалізація

Ось базова реалізація — її ми й розбираємо рядок за рядком:

```python
def merge_sort(arr):
    if len(arr) <= 1:
        return arr

    mid = len(arr) // 2
    left_half = arr[:mid]
    right_half = arr[mid:]

    return merge(merge_sort(left_half), merge_sort(right_half))

def merge(left, right):
    merged = []
    left_index = 0
    right_index = 0

    # Спочатку об'єднайте менші елементи
    while left_index < len(left) and right_index < len(right):
        if left[left_index] <= right[right_index]:
            merged.append(left[left_index])
            left_index += 1
        else:
            merged.append(right[right_index])
            right_index += 1

    # Якщо в лівій або правій половині залишилися елементи,
    # додайте їх до результату
    while left_index < len(left):
        merged.append(left[left_index])
        left_index += 1

    while right_index < len(right):
        merged.append(right[right_index])
        right_index += 1

    return merged

print(merge_sort([5, 3, 8, 4, 2]))   # [2, 3, 4, 5, 8]
```

Що тут що:

- `if len(arr) <= 1: return arr` — **базовий випадок**: список із 0 або 1 елемента вже відсортований;
- `mid = len(arr) // 2` — середина: ділимо **строго навпіл за позицією**;
- `left_half = arr[:mid]`, `right_half = arr[mid:]` — дві половини;
- `return merge(merge_sort(left_half), merge_sort(right_half))` — рекурсивно сортуємо обидві половини й **зливаємо** результати;
- у `merge` перший `while` порівнює «голови» двох списків і додає менший у `merged` (за рівності — з **лівої** половини, тому сортування стабільне), а два наступні `while` «доливають» залишок того списку, що не вичерпався.

Навчальна версія `merge_sort_steps` повторює цей код **дія в дію**, але будує **журнал/дерево** подій поділу й злиття разом із лічильниками порівнянь, додавань і глибини — саме з цих подій зібрані всі картинки нижче.

### Як читати кадри

- 🔵 **сині комірки** — елементи **лівої** половини (`left`);
- 🟧 **помаранчеві комірки** — елементи **правої** половини (`right`);
- 🟡 **бурштинова комірка** — поточна менша «голова», яку саме додають у `merged` (вона ж з'являється останньою в результаті);
- 🟢 **зелені комірки** — відсортований / уже злитий результат;
- ⬜ **сіро-сині комірки** — базовий випадок (поодинокий елемент) або вже спожитий елемент половини;
- ▲ **курсори** під комірками — вказівники `left_index` / `right_index`.

### Дерево рекурсії та трасування

Спершу `merge_sort` рекурсивно ділить масив навпіл (фаза **поділу**, вниз), а потім зливає відсортовані половини (фаза **злиття**, вгору). Усе разом — **дерево рекурсії**. Поділ завжди строго навпіл, тож дерево ідеально збалансоване:

![Дерево рекурсії масиву [8, 4, 6, 2, 7, 1, 5, 3]](docs/images/tree_intro.png)

```text
3       merge_sort  [8, 4]                    1    [8]           [4]
```

### Зіркова операція: злиття двома вказівниками

## 5. Гарантія $O(n\log n)$ без виродження

Найважливіша властивість сортування злиттям — **гарантований** $O(n\log n)$ у **всіх** випадках. Покажімо це детальніше на самій операції злиття та порівняймо зростання зі швидким сортуванням:

![Розбір однієї операції злиття двома вказівниками](docs/images/merge_step_grid.png)

```text
Окрема операція merge: [3, 5] + [2, 4, 8]
Злиття [3, 5] + [2, 4, 8] = [2, 3, 4, 5, 8] (4 порівнянь)
```

Чому складність не вироджується? **Дерево завжди збалансоване** (поділ строго навпіл), тож глибина завжди $\log_2 n$, а на кожному рівні злиття опрацьовує $n$ елементів. Підставмо різні входи однакового розміру $n = 8$:

| Вхід | Глибина | Злить | Додавань | Порівнянь |
|---|---|---|---|---|
| `[8, 4, 6, 2, 7, 1, 5, 3]` (випадковий) | 3 | 7 | 24 | 17 |
| `[1, 2, 3, 4, 5, 6, 7, 8]` (відсортований) | 3 | 7 | 24 | 12 |
| `[8, 7, 6, 5, 4, 3, 2, 1]` (зворотний) | 3 | 7 | 24 | 12 |

Глибина, кількість злить і додавань **однакові** для будь-якого порядку — структура роботи не залежить від даних. Порівнянь у відсортованому/зворотному випадку навіть трохи менше (одна половина щоразу «виграє» першою), але це й близько не $O(n^2)$:

![Графік: гарантований n·log n проти n²](docs/images/growth.png)

Синя смуга — сортування злиттям: воно завжди між найкращим ($\approx \tfrac12 n\log_2 n$) і гіршим ($\approx n\log_2 n$) випадками. Червона крива — гірший випадок quicksort ($\approx n^2/2$): **саме його в merge sort не буває**. Це ключовий контраст: quicksort у середньому швидший на практиці, але **може** виродитися до $O(n^2)$; merge sort — **ніколи**.

## 6. Стабільність: масив із дублікатами

Сортування **стабільне**, якщо воно зберігає взаємний порядок елементів із **однаковими ключами**. Merge sort стабільний завдяки **нестрогому** порівнянню `left[left_index] <= right[right_index]`: коли голови половин рівні, ми беремо елемент із **лівої** половини першим, тож елементи, що стояли раніше, лишаються раніше.

Щоб це побачити, візьмемо «мічені» дублікати — кожна копія значення має підрядковий номер, що показує її початкове місце (`3₁`, `3₂`, `3₃`):

```text
Стабільність на масиві з дублікатами
Вхід (підписи показують початковий порядок рівних ключів): [3₁, 1₁, 3₂, 2₁, 1₂, 3₃]
Вихід (рівні ключі зберегли початковий порядок): [1₁, 1₂, 2₁, 3₁, 3₂, 3₃]
Стабільно ✓: серед рівних ключів порядок підписів не змінився.
```

Найкраще видно на злитті верхнього рівня: коли голови обох половин мають рівний ключ, перемагає **ліва** (за `<=`), тож `3₁` стає перед `3₂`, а `3₂` — перед `3₃`:

![Злиття на рівні кореня: рівні ключі — з лівої половини першими](docs/images/merge_duplicates.png)

![Відсортований масив: рівні ключі в початковому порядку](docs/images/result_duplicates.png)

Стабільність важлива, коли елементи несуть додаткові дані (сортуємо записи за одним полем, не руйнуючи попереднього впорядкування за іншим). Саме тому стабільний merge sort — основа промислових сортувань. Дерево рекурсії для цього прикладу — [`docs/images/tree_duplicates.png`](docs/images/tree_duplicates.png).

## 7. Низхідний проти вихідного (bottom-up) → місток до TimSort

Розібрана вище версія — **низхідна рекурсивна** (top-down): вона ділить масив згори вниз, а зливає на зворотному ході рекурсії. Той самий алгоритм можна записати **без рекурсії** — **вихідним** способом (bottom-up): рахуємо кожен елемент відсортованою «пробіжкою» (run) довжини 1 і зливаємо сусідні пробіжки в пробіжки довжини 2, потім 4, 8, … — аж поки одна пробіжка не накриє весь масив:

```python
def merge_sort_bottom_up(arr):
    a = list(arr)
    n = len(a)
    width = 1
    while width < n:
        for lo in range(0, n, 2 * width):
            mid = min(lo + width, n)
            hi = min(lo + 2 * width, n)
            a[lo:hi] = merge(a[lo:mid], a[mid:hi])
        width *= 2
    return a
```

На розмірах-степенях двійки розбиття на блоки збігається з низхідним поділом навпіл, тож **результат і кількість порівнянь ідентичні** (для нашого масиву — ті самі 17 порівнянь). Вихідна версія прибирає накладні витрати рекурсії й, головне, є **прямим містком до TimSort**: той теж зливає відсортовані пробіжки знизу вгору — лише спершу знаходить (і за потреби добудовує сортуванням вставками) природні впорядковані пробіжки у вхідних даних.

## 8. Покрокове виконання коду: панелі «код ↔ дані»

Приклади вище показували *результат* кожного кроку. Тут — **сам код у дії**: ліворуч фрагмент алгоритму з **підсвіченими активними рядками**, праворуч — дані саме в цей момент. **Колір рядка коду кодує, що відбувається:** 🟡 рядок виконується зараз; 🔵/🟧 поділ на `left_half` / `right_half`; 🟡 додавання меншого елемента в `merged`; 🟢 повертаємо відсортований список. Під час поділу праворуч — рядок комірок підмасиву; під час злиття — **зіркова панель** двох вказівників.

Будуємо це для масиву-приклада `[5, 3, 8, 4, 2]` (його трасування рядок-у-рядок збігається з розбором вище). Трасування дерева для цього масиву:

```text
Рівень  Функція     arr              mid  left_half  right_half
------  ----------  ---------------  ---  ---------  ----------
```

## 10. Складність і властивості

| Випадок | Час | Чому |
|---|---|---|
| **Найкращий** | $O(n\log n)$ | дерево завжди збалансоване — навіть на впорядкованому вході робляться всі поділи й злиття |
| **Середній** | $O(n\log n)$ | $\log n$ рівнів × $n$ роботи на рівень |
| **Гірший** | $O(n\log n)$ | виродженого випадку **не існує** (на відміну від quicksort) |

Інші властивості:

- **Додаткова пам'ять — $O(n)$:** `merge` будує **новий** список `merged`, тож метод **не on-place** (це головний компроміс проти in-place quicksort з $O(\log n)$ пам'яті).
- **Стабільне:** рівні ключі зберігають взаємний порядок (за рівності беремо з лівої половини, `<=`).
- **Не адаптивне** (у базовій формі): на вже відсортованих даних усе одно робляться всі поділи й злиття. Адаптивність додає вже TimSort (виявляє готові пробіжки → $O(n)$ на впорядкованому вході).

Кількість порівнянь у будь-якому разі росте як $n\log_2 n$. Порівняймо це зростання з $n^2/2$ (гірший випадок quicksort):

| `n` | Merge sort ($\approx n\log_2 n$) | Quicksort гірший ($\approx n^2/2$) | У скільки разів краще |
|---|---|---|---|
| 10 | ≈ 33 | 45 | ~1× |
| 100 | ≈ 664 | 4 950 | ~7× |
| 1 000 | ≈ 9 966 | 499 500 | ~50× |
| 10 000 | ≈ 132 877 | ≈ 50 000 000 | ~375× |
| 1 000 000 | ≈ 2·10⁷ | ≈ 5·10¹¹ | ~25 000× |

## 11. Обмеження: ціна пам'яті й неадаптивність

Гарантований $O(n\log n)$ і стабільність даються не безплатно:

- **$O(n)$ додаткової пам'яті** — головна вада. Кожне злиття будує новий список, тож потрібен буфер розміром із масив. Для величезних масивів у пам'яті це суттєво (in-place quicksort обходиться $O(\log n)$). Існують in-place варіанти злиття, але вони складні й повільніші на практиці.
- **Неадаптивність базової версії:** merge sort не «помічає», що вхід уже майже впорядкований, — він однаково робить усі поділи й злиття. (Це виправляє TimSort, виявляючи природні пробіжки.)
- **Накладні витрати рекурсії** на малих підмасивах: вартість виклику функції починає домінувати. Пом'якшує це **вихідна (bottom-up)** версія й перемикання на сортування вставками для коротких відрізків — саме так і робить TimSort.

Попри це, **гарантований** $O(n\log n)$ і **стабільність** роблять merge sort основою промислових сортувань там, де передбачуваність важливіша за константу чи пам'ять.

## 12. Де це доречно

Merge sort особливо сильний там, де quicksort слабкий:

- **Зовнішнє сортування** (дані не вміщуються в пам'ять): merge sort природно зливає відсортовані «прогони» з диска/стрічки — це класична схема сортування великих файлів.
- **Зв'язні списки:** злиття не потребує довільного доступу за індексом, тож список можна відсортувати за $O(n\log n)$ **без** додаткової пам'яті на масив (лише перепризначенням посилань).
- **Потрібна стабільність** і **гарантована** поведінка (наприклад, у бібліотеках, де неприйнятний випадковий $O(n^2)$).
- **Паралелізм:** незалежні половини можна сортувати на різних ядрах/машинах, а потім злити.

## 13. Фінал серії: TimSort і вся картина сортувань

Стандартні `sorted()` і `list.sort()` у Python використовують **TimSort** — гібрид, що поєднує **сортування вставками** й **сортування злиттям** (розробив Тім Пітерс, 2002). Ідея: масив ділиться на короткі «пробіжки» (runs), кожна доводиться до відсортованого стану **сортуванням вставками** (воно швидке на коротких і майже впорядкованих відрізках), а тоді відсортовані пробіжки **зливаються** між собою сортуванням злиттям знизу вгору — доти, доки не лишиться одна. TimSort бере найкраще з двох методів: адаптивність і малу константу вставок на коротких/упорядкованих даних та гарантований $O(n\log n)$ і стабільність злиття. На вже відсортованому вході він виявляє готові пробіжки й працює за $O(n)$; пам'ять — $O(n)$.

Так уся серія простих і ефективних сортувань складається в одну картину — від найпростішого до промислового стандарту:

| Алгоритм | Найкращий | Середній | Гірший | Пам'ять | Стабільний | Адаптивний | In-place |
|---|---|---|---|---|---|---|---|
| [Бульбашкове](https://github.com/MarynaShavlak/algo-bubble-sort) | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | так | так¹ | так |
| [Вставками](https://github.com/MarynaShavlak/algo-insertion-sort) | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | так | так | так |
| [Вибором](https://github.com/MarynaShavlak/algo-selection-sort) | $O(n^2)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | ні | ні | так |
| [Швидке (quicksort)](https://github.com/MarynaShavlak/algo-quick-sort) | $O(n\log n)$ | $O(n\log n)$ | $O(n^2)$ | $O(\log n)$ | ні | ні | так |
| **Злиттям (merge sort)** | $O(n\log n)$ | $O(n\log n)$ | $O(n\log n)$ | $O(n)$ | **так** | ні | ні |
| **TimSort** (`sorted`) | $O(n)$ | $O(n\log n)$ | $O(n\log n)$ | $O(n)$ | **так** | **так** | ні |

<sub>¹ бульбашкове сортування адаптивне лише в оптимізованій версії з прапорцем ранньої зупинки.</sub>

## 14. Підсумок

- **Сортування злиттям** працює за принципом «розділяй і володарюй»: ділить масив навпіл, рекурсивно сортує обидві половини й **зливає** їх двома вказівниками (вся робота — у фазі злиття, **після** рекурсії — дзеркально до quicksort).
- Поділ строго навпіл за позицією робить дерево рекурсії **завжди збалансованим** (глибина $\log n$), тому складність — **гарантований $O(n\log n)$ у будь-якому випадку**: виродженого $O(n^2)$, як у quicksort, тут немає.
- Метод **стабільний** (за рівності голів беремо з лівої половини, `<=`) і коштує $O(n)$ **додаткової пам'яті** — він **не on-place**.
- Базова версія **не адаптивна**; **вихідна (bottom-up)** версія прибирає рекурсію й веде прямо до **TimSort** — гібрида вставок і злиття, що є стандартним `sorted()` у Python.
- На масиві `[8, 4, 6, 2, 7, 1, 5, 3]` сортування коштує **17 порівнянь, 24 додавання, 7 злить** за глибини рекурсії **3**.
- Merge sort — основа промислових сортувань там, де потрібні **гарантована** поведінка, **стабільність**, зовнішнє сортування чи сортування зв'язних списків.
